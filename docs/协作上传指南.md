# 五人协作与上传指南

新仓库地址：`https://github.com/coderdingyu/chengjing-team`。它是私人仓库，负责人需在 GitHub 仓库 `Settings → Collaborators and teams → Add people` 中邀请另外四位成员；成员接受邀请后才能推送自己的分支。参考系统地址：`https://github.com/coderdingyu/chengjing`，请从中迁移自己任务需要的代码与思路。

## 每个人第一次做

1. 用**自己的 GitHub 账号**接受协作邀请。克隆团队仓库：

   ```powershell
   git clone https://github.com/coderdingyu/chengjing-team.git
   cd chengjing-team
   git remote add reference https://github.com/coderdingyu/chengjing.git
   git fetch reference main
   ```

2. 在这份仓库里设置自己的姓名和与 GitHub 账号关联的邮箱：

   ```powershell
   git config user.name "你的姓名或 GitHub 用户名"
   git config user.email "你在 GitHub 验证过的邮箱"
   ```

3. 启动骨架并确认构建通过。Windows 启动方式见根目录 `README.md`。旧仓库只用来查看参考实现；不要直接把其整个目录拷进新仓库。

## 每完成一个功能，形成一次自己的提交

以成员 B 的 `B01` 岗位案例为例；其他成员把编号与英文短名替换成自己的任务：

```powershell
git switch main
git pull --ff-only origin main
git switch -c feat/B01-job-cases
# 实现 B01 的代码、测试、必要文档
cd frontend
npm run build
cd ..\backend
.\mvnw.cmd -s .mvn/settings.xml test
cd ..
git status --short
git add backend/src/main frontend/src/features/preparation docs/30项功能分工.md
git diff --cached --check
git diff --cached --stat
git commit -m "feat(B01): 增加岗位案例目录"
git push -u origin feat/B01-job-cases
```

随后在 GitHub 打开新出现的 `Compare & pull request`，PR 标题写任务编号和功能，正文说明“完成了什么、怎么验证、是否改了公共契约”。负责人检查并合并到 `main`。下一项从**最新 `main` 新开分支**。每人最终应有 6 个不同的功能提交，5 人共 30 个；骨架提交由负责人创建，但不算进个人 6 项。

如果使用 GitHub 的 **Squash and merge**，一个 PR 应只有一个功能提交，合并前核对合并提交的作者信息。若要让 GitHub 历史清楚显示五位开发者各自的原始提交，可选择 **Rebase and merge** 并检查作者；不要用负责人的本机配置代替组员署名。私有仓库的贡献图显示还受各人 GitHub 设置影响，仓库提交历史始终可以核对作者。

## 协作顺序

1. 负责人先合并 E01 的持久化基础和 E02 的模型配置接口；A/B/C/D 可以同时在各自目录实现第一项，不必等所有人完成。
2. A02 登录完成后，其余模块接入当前用户 ID；B01 案例完成后 C01 面试房间可接案例 ID；C02 文本回答完成后 D02 才接评分。
3. 任何共享 DTO、数据库迁移、路由或 `frontend/src/App.tsx` 的变更，要在 PR 中写影响的模块，避免两人同时修改同一段入口代码。
4. 当 `main` 已更新，自己的未合并分支可执行 `git fetch origin`、`git rebase origin/main`、重新运行检查；只对自己独占的分支改写提交。
5. 每次提交前查看 `git diff --cached`，确保没有 `.env`、密钥、数据库、真实简历和个人音视频。源码参考中的测试账号只能用于本地合成数据。

## AI 工具上传遇到 `403 Resource not accessible by integration`

这个报错通常来自 AI 工具使用的 GitHub App／集成令牌。仓库协作者的写权限与**应用本身**的仓库访问范围、Contents 写权限、Pull requests 写权限是不同的授权；把仓库设为公开只开放读取，不会给应用写入权限。不要为了绕过 403 把个人令牌发给 AI 对话，也不要直接在 `main` 上重试推送。

先保留本地提交并在成员自己的终端检查：

```powershell
git status --short --branch
git log -1 --oneline
git branch --show-current
git remote -v
```

确认 `origin` 是 `https://github.com/coderdingyu/chengjing-team.git`，最新提交是本人的功能代码。如果当前已经在 `feat/编号-英文短名` 分支，用该成员自己的 GitHub 身份执行 `git push -u origin HEAD`。如果当前在 `main`，先从当前提交新建功能分支，例如 `git switch -c feat/B01-job-cases`，再执行 `git push -u origin HEAD`。这不会丢掉当前提交。推送前可运行 `git fetch origin main` 和 `git log --oneline origin/main..HEAD`，确认 PR 只含本人这项功能。首次通过 HTTPS 推送时，使用 Git Credential Manager 的浏览器登录或个人 SSH 配置，确认登录的是该成员自己的 GitHub 账号；`git config user.name` 只设置提交作者，不等于登录授权。推送成功后在 GitHub 网页从该分支向 `main` 创建 PR，不依赖 AI 集成创建 PR。

如果确实要让 AI 集成直接推送，仓库所有者在 `chengjing-team → Settings → GitHub Apps` 找到**该工具对应的具体应用**，查看它是否安装在 `coderdingyu` 名下、是否选择了 `chengjing-team`，并核对 Contents 与 Pull requests 是否具备写权限。只有应用本身申请了相应权限，安装者才能批准；页面没有该权限时需要应用提供方更新权限，不能靠添加协作者补上。按最小范围只授权此仓库。参考 [GitHub App 安装与权限说明](https://docs.github.com/en/apps/using-github-apps/reviewing-and-modifying-installed-github-apps) 与 [GitHub App 权限规则](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app)。
